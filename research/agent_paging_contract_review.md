## Conclusion

**No confirmed blocker to treating #56 as host-only research.** Its page-entry encoder, leaf table, synthetic walk, and integration test are explicitly labeled as models/scaffolding. They do not install tables or change `CR3`; their passing tests cannot validate x86-64 hardware behavior. The paging-transition contract is appropriately framed as future work and lists critical prerequisites, but those prerequisites are not implemented or proved by these models.

**Blocking before any future `CR3` transition:** demonstrate that every failed preflight or table-build path exits without a `CR3` write, and separately establish actual mappings, CPU permission state, and physical-frame ownership. This is an implementation acceptance gap, not a defect in the current host-only experiment.

The integration test manually decodes only present/write/user/address bits and labels itself test scaffolding, not a hardware decoder ([test](https://github.com/bit-foundry-labs/embers-kernel/blob/ad0723997611346cbb71741212b4291034498dc0/rust-kernel/tests/page_research_integration.rs#L1-L2), [decoder](https://github.com/bit-foundry-labs/embers-kernel/blob/ad0723997611346cbb71741212b4291034498dc0/rust-kernel/tests/page_research_integration.rs#L47-L65)). Unit tests for simulated writes therefore should not be described as hardware permission tests.

## Negative-test priority before any transition

1. **Smallest deterministic gate test:** exercise a side-effect-free transition preflight with invalid mode/provenance/build inputs and a test `CR3` writer/spying boundary. Assert each rejection returns before the writer is called and leaves the old root unchanged. Existing mode tests cover selected `PG`/`PAE`/`LA57` rejection, but do not test a transition gate or prove that no write occurred.
2. Before any privileged switch, reject unsupported physical widths/reserved encodings, noncanonical addresses, missing mappings, duplicate/overlapping or unowned frames, and incomplete table construction; assert no partial root publication, frame reuse, or `CR3` write.
3. Keep actual hardware evidence separate: a gated QEMU transition must verify root read-back, live code/data/stack and fault-path survival, and expected fault behavior. Host models alone cannot establish that evidence.

The contract already proposes no-write failure observations and a separate missing-mapping fault profile ([future tests](https://github.com/bit-foundry-labs/embers-kernel/blob/ad0723997611346cbb71741212b4291034498dc0/docs/PAGING_TRANSITION_V1.md#L47-L61)). The first priority above makes the no-write invariant directly testable before introducing a privileged switch.

## Draft overlap and integration risk

- #55 and #56 are independent from the same `main` base (`e30e9128b13518c7cf0671a708251598a905e084`); their merge base is that commit. Both add the same `LeafTable`/`TableError` insertion model and tests in `rust-kernel/research/page_entry.rs` ([#55 file](https://github.com/bit-foundry-labs/embers-kernel/blob/1489ec27184080b756074c6fd93bcb3af776fa72/rust-kernel/research/page_entry.rs#L29-L73), [#56 file](https://github.com/bit-foundry-labs/embers-kernel/blob/ad0723997611346cbb71741212b4291034498dc0/rust-kernel/research/page_entry.rs#L29-L73)). This is direct overlapping work in one file; naïvely combining the additions risks duplicate definitions/tests or patch conflicts. No merge is recommended here.
- #56's allocator handoff note is proposal-only. The parallel #59 draft says its boot-owner move still permits independently constructed overlapping pools and is not global frame authority ([#59 description](https://github.com/bit-foundry-labs/embers-kernel/pull/59)). Treat that ownership gap as unresolved, not as a satisfied dependency or guarantee.
- The proposed #61 contract reinforces exact-revision review, explicit test scope, and human review; it is guidance, not a security or authorization boundary ([#61 `AGENTS.md`](https://github.com/bit-foundry-labs/embers-kernel/blob/97465943986ddd2c497356cc70955c9ff9e60ece/AGENTS.md#L13-L21)).
